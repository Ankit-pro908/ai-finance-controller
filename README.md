# AI Finance Controller

**Evidence-first investigation of payment reconciliation exceptions.**
The AI proposes a cause. Evidence checks, a consistency check, simulation, and a safety gate decide whether it is safe to resolve.

**🚀Live demo:** https://ai-finance-controller-908.streamlit.app/
**📦GitHub:** https://github.com/Ankit-pro908/ai-finance-controller



---

## At a glance

| | |
|---|---|
| **Problem** | Reconciliation can tell you two records disagree. It cannot tell you *why*, or whether a fix is safe. |
| **Approach** | A deterministic reconciliation engine first. An LLM only for ambiguous exceptions. Every AI claim is validated, simulated, and gated. |
| **Outputs** | `RESOLUTION_CANDIDATE` or `HUMAN_REVIEW`. The controller never edits real financial data. |
| **Exception types** | Duplicate payment, fee mismatch, refund mismatch, settlement amount mismatch, missing settlement, missing ledger entry |
| **Stack** | Python 3.11, pandas, Streamlit, Groq API (`openai/gpt-oss-120b`, temperature 0) |
| **Data** | Synthetic payment, fee, refund, settlement, and ledger records (INR), generated by `src/data_generator.py` |

---

## The problem

A single payment is spread across several sources:

```
Payment --- Fee --- Refund --- Settlement --- Ledger
```

When the totals do not match, one discrepancy can have several plausible explanations. A ₹50 settlement gap could be a wrong fee, a wrong refund, or a bad ledger entry. Fixing the wrong record makes the books look right while hiding the real error.

This project treats that as an **investigation problem**, not a text-generation problem. The LLM is never trusted as a source of financial truth.

---

## How it works

```
Deterministic reconciliation  ->  Exception detected
            |
            v
     Evidence retrieval  (payment, fee, refund, settlement, ledger)
            |
            v
   Hypothesis generation  (LLM for ambiguous cases, rules otherwise)
            |
            v
   Evidence validation    (do the cited record IDs and values exist?)
            |
            v
   Causal consistency check (does the claimed change match the observed gap?)
            |
            v
   Counterfactual simulation (apply the change to a copy and recompute)
            |
            v
        Safety gate
        /         \
RESOLUTION_CANDIDATE   HUMAN_REVIEW
```

1. **Deterministic first.** Known relationships (expected settlement, ledger totals, duplicate detection) are handled by rules.
2. **Evidence retrieval.** The relevant payment, fee, refund, settlement, and ledger records are collected for the case.
3. **Hypothesis generation.** For difficult cases, the LLM returns structured hypotheses: root cause, affected records, observed and proposed values, and a claimed delta.
4. **Evidence validation.** Every cited record ID, field, and observed value is checked against the source data.
5. **Causal consistency check.** The proposed change and the claimed delta must both match the size of the observed reconciliation difference. This is a necessary check, not proof. The code states that it "does NOT prove the hypothesis".
6. **Counterfactual simulation.** The change is applied to a deep copy of the datasets and the full reconciliation is recomputed. The exception must clear without creating a new inconsistency elsewhere.
7. **Safety gate.** `decision_policy.py` combines the AI's confidence and evidence-sufficiency flag with deterministic signals: evidence completeness, citation validity, and conflicts between records. Ambiguity, conflict, invalid citations, or missing evidence lead to `HUMAN_REVIEW`.

### Investigation modes

Each case records how it was investigated:

| Mode | Meaning |
|---|---|
| `DETERMINISTIC` | Resolved by the rule-based path. No LLM call. |
| `AI` | The LLM generated hypotheses that went through the full validation pipeline. |
| `AI_FALLBACK_DETERMINISTIC` | The AI path was attempted but failed (for example a missing API key or API error), so deterministic fallback hypotheses were used. If none exist, the case goes to `HUMAN_REVIEW`. |

An API failure never silently becomes a financial resolution.

## Worked examples

These are real outputs from the unseen suite.

### 1. Simulation rejects a plausible but wrong fix (U002)

Ground truth: an unexpected ledger adjustment. The ledger is ₹25 short of the settlement. A hypothesis proposes that the settlement ledger entry is missing and adds one for ₹4,065.04.

| | Before | After simulated fix |
|---|---|---|
| Ledger net | 4,040.04 | 8,105.08 |
| Ledger difference | -25.00 | 4,040.04 |
| Exception cleared | No | No |

The simulation returns `NO_RESOLUTION`. The idea sounded reasonable, but recomputing the ledger shows it makes things worse. The final decision is `HUMAN_REVIEW`.

### 2. Several fixes clear the same gap, so the controller does not guess (U005)

Ground truth: multiple plausible causes. Expected settlement is ₹5,440.60 but the recorded settlement is ₹5,540.60, a ₹100 gap. Two hypotheses each clear it in simulation:

| Hypothesis | Change |
|---|---|
| H1: fee error | Fee 220.48 to 120.48 |
| H2: refund error | Refund 2,862.92 to 2,762.92 |

The arithmetic cannot tell a fee error from a refund error. The controller does not pick one and returns `HUMAN_REVIEW`.

### What these numbers do and do not show

- **The 500/500 mainly validates the deterministic controller.** Only 12 of 500 cases (2.4%) reached the LLM.
- **The unseen suite tests abstention only.** All five cases expect `HUMAN_REVIEW`, so a controller that always escalated would also score 5/5. It does not yet test whether the controller resolves unfamiliar cases correctly.
- **The stress suite is a regression suite, not a held-out test.** Failures found on it (for example S002, where a refund hypothesis also cleared a ₹50 gap) were fixed during development. See [development notes](docs/development-notes.md).
- **All data is synthetic**, generated by the scripts in `src/` with injected errors. The ground truth was written by the same author as the controller.

## Design principles

1. **Deterministic first.** Known financial relationships use rules.
2. **Evidence before conclusions.** An explanation must be grounded in real records.
3. **Validate every citation.** Cited IDs and values must match the source data.
4. **Check consistency.** The proposed cause must explain the observed difference.
5. **Simulate before resolving.** A correction must survive counterfactual testing.
6. **Never guess through ambiguity.** Competing explanations go to a human.
7. **Never modify real financial data.** Investigation changes stay hypothetical until an explicit approval process exists.

---

## The AI layer

- **Model:** `openai/gpt-oss-120b` via the Groq API, `temperature=0`. This is a general-purpose model guided by payment-specific prompts and a structured response schema. It is **not** fine-tuned on payment data.
- **Bounded retries:** at most 2 API attempts per call (`MAX_API_ATTEMPTS` in `src/ai/client.py`). If the AI still fails, the orchestrator uses deterministic fallback hypotheses, or returns `HUMAN_REVIEW` when none exist.
- **Structured output:** responses are parsed and checked by a response validator before they are used.
- **Reproducibility:** temperature 0 makes output near-deterministic, but LLM output can still vary between runs.

## Getting started

Tested with Python 3.11, streamlit 1.63.0, pandas 3.0.5, numpy 2.4.6, groq 1.7.0, pytest 9.1.1.

```bash
git clone https://github.com/Ankit-pro908/ai-finance-controller.git
cd ai-finance-controller
python -m venv .venv
# Windows: .venv\Scripts\activate    macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
pip install pytest
```

Set your Groq API key (never commit it):

```bash
# macOS/Linux
export GROQ_API_KEY="your_key"
# Windows PowerShell
$env:GROQ_API_KEY = "your_key"
```

Without a key the evaluation scripts still run, but cases that need the LLM fall back to the deterministic path (`AI_FALLBACK_DETERMINISTIC`).

```bash
streamlit run app.py              # investigation console
python tests/run_unseen.py        # unseen suite
python tests/stress_runner.py     # 500-case stress suite (LLM cases make live API calls, so it can be slow)
pytest -q                         # unit tests
```

On Windows PowerShell, run `$env:PYTHONUTF8 = "1"` first if the stress runner fails with a `UnicodeEncodeError`.

## Limitations

- **Synthetic data only.** No real payment-processor formats, partial settlements, batching, currency conversion, or timing differences.
- **Small LLM footprint in the benchmark.** The AI path was exercised on 12 stress cases and 4 unseen cases.
- **The unseen suite has no case that should be resolved.** It currently measures only correct abstention.
- **The consistency check is magnitude-based.** It compares the size of the proposed change, the claimed delta, and the observed difference. It does not independently check the claimed direction, so counterfactual simulation is the real safeguard against wrong-direction fixes.
- **An LLM can be confidently wrong.** Evidence validation, simulation, and the safety gate reduce this risk but do not remove it.
- **External API.** Real deployments would send financial records to an LLM provider, which needs masking or a self-hosted model.
- **No audit log or approval workflow yet.**

---

## Who this is for

Payment operations and finance teams who investigate reconciliation exceptions by hand. The console shows each hypothesis, the evidence behind it, and the simulation result, so a reviewer can check the reasoning instead of rebuilding it.

---

## Roadmap

- Add unseen cases that should end in `RESOLUTION_CANDIDATE`, and a held-out set that is never used for tuning.
- Report false-resolution rate and correct-abstention rate separately.
- Compare rules-only, LLM-only, and the full controller on the same cases.
- Historical resolution memory: store approved resolutions as precedents for retrieval.
- Human-in-the-loop learning that improves hypotheses but can never bypass the safety gate.
- Production controls: approval workflows, role-based access, immutable audit logs, model version tracking.
